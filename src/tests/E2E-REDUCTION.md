# E2E reduction plan

Keep Playwright for behavior that depends on the real browser, Next runtime, and persisted data together. Test
individual rules at the lowest level that can reproduce the failure. A browser may still be necessary for CSS, focus,
touch, and accessibility, but those checks usually do not need the application server and MongoDB.

The pre-reduction Playwright inventory listed **92 scenarios in 17 files**, with **222 project entries** (92 desktop
Chromium, 65 mobile Chromium, 65 mobile WebKit). These are discovered entries, including tests skipped at runtime. Use
this as a baseline for scope and measure actual CI time separately.

## Migration order and acceptance

1. **Cut browser repetitions (done).** Both mobile projects select four `@mobile` scenarios covering touch navigation,
   app and review safe areas, and simulated keyboard viewport. Desktop Chromium still runs the axe scans in the
   functional CI job. Playwright now lists 96 project entries (88 desktop and four per mobile engine).
2. **Remove low-risk duplicates (done).** Removed five desktop scenarios and trimmed two others. Playwright lists 91
   project entries (83 desktop and four per mobile engine).
    - `ToolbarMenu.test.tsx` covers utilities and generated filter links. Playwright retains actual navigation with
      filters and Escape dismissal.
    - `AmountBox.test.tsx` and `AmountVariantsTab.test.tsx` cover tab switching, expansion and cancelling a move. Both
      history tab tests check populated tables for the absence of column headers.
    - `ProductBox.test.tsx` covers the expiry draft across collapse and reopen. `ProductsGrid.test.tsx` and
      `ProductTile.test.tsx` cover parent expansion and collapse.
    - `ReviewTable.test.tsx` covers selection controls. `ReviewBox.test.tsx` verifies that applying after a reset sends
      no changes. Playwright retains tooltip geometry and the persisted review flow.
    - `AmountVariantsTab.test.tsx` and `ProductYearBar.test.tsx` already cover drafts across years, nonannual amount
      aggregation, and historical-year selection. Use those tests as the starting point for future annual logic changes.
3. **Move data integrity cases before removing them.** Reuse the temporary replica-set approach in
   `src/tests/playwright/start-server.ts` for a focused Vitest integration suite with no Next process. The existing data
   tests often use `vitest/fakeDb.ts` (Mingo), including parts of the current action integration coverage. Prioritize
   source/destination balances and copied metadata, rename cascades, September aggregation boundaries, and rejected
   imports leaving persisted data intact. Prove each replacement catches the original regression before removing its
   browser case.
4. **Move layout checks to a real browser with fixture data.** Use the existing Vitest browser setup and add a focused
   browser project for interaction or geometry assertions if needed. Keep screenshot comparisons in the visual project
   and avoid moving CSS layout assertions to jsdom. Keep the existing Playwright case until the replacement reproduces
   the critical state.
5. **Rebalance the smoke suite.** Aim for roughly 8–12 desktop journeys and 2–4 explicitly selected journeys per mobile
   engine, outside the separate axe and visual runs. Retag `@critical` around the remaining journeys rather than
   carrying over the present CRUD tags. Compare listed counts, pass/fail results and CI duration before and after, with
   `pnpm test`, the targeted MongoDB checks, Playwright smoke, and axe. Treat counts as a sizing target, and keep
   coverage in place if the proposed replacement misses an important assertion.

Reclassify the open items in [PLAN.md](PLAN.md) before adding more Playwright cases. Category options, copy conflicts,
parent restrictions, review batches, and file validation belong in component or server integration tests. Test real drag
or mobile gestures in a browser only where they are supported and user-critical. Production authorization can be
exercised at the request/server boundary with controlled identities. A browser sign-in smoke is justified only if the
cookie/redirect round trip adds a distinct check, and requires a controlled environment because the current development
server bypasses authentication.
