# Docker logs in Grafana Cloud Loki

The supplied Docker integration uses Alloy to collect stdout/stderr from the `rusys-app` Compose project, including both
application slots, MongoDB, the gateway, and Alloy itself. Collection follows container recreation through Docker
discovery. Stopped slots retain their previously ingested history; they produce new logs only while running.

For another hosting platform, forward the same structured application events through its supported log collection
interface. Container discovery and gateway access logging belong to this Docker integration.

## Credentials and deployment

Keep `GC_LOKI_URL`, `GC_LOKI_USER`, and `GC_LOKI_TOKEN` in the target environment's secret store; Compose deployments
inject them through a private `.env`. The URL must be the Grafana Cloud Loki push endpoint ending in
`/loki/api/v1/push`; the username is the logs instance ID, and the token needs `logs:write`. Compose passes these values
only to `monitoring`. Do not copy them into application environment files, source code, images, or browser variables.
The existing Grafana administration credential in `.env.grafana.local` is separate and is used only for administration
and read-only verification.

The existing deployment command uploads and validates Alloy configuration before recreating monitoring and building the
inactive application slot. Follow the [deployment guide](../DEVELOPMENT-AND-DEPLOYMENT.md#deployment-and-rollback).
Application logging is part of the application build; collector configuration does not modify application images.

## Privacy and useful context

The Node logger emits one JSON object per line with timestamp, severity, a static event name, `service`, `slot`, and
release `version`. Slots come from each Compose service's runtime environment. The version comes from `APP_VERSION`
baked into the image, so rollback retains the previous release's identity.

Logging uses an allowlist: arbitrary strings, request objects, headers, cookies, tokens, user data, error messages, and
stacks are omitted. Add diagnostic context through bounded enums and validated numeric fields. Do not pass personal data
to the logger. Runtime console calls are reduced to static events before application output is emitted.

Alloy applies a second privacy boundary before writing to Cloud. Framework output and service logs that cannot be proven
safe become structured redaction events. Infrastructure diagnostics retain only explicitly selected fields; client
addresses, query strings, MongoDB attributes, and arbitrary messages never reach Loki. This deliberately limits
free-text debugging: a redaction event indicates that output occurred, but cannot recover its original text. Existing
local Docker logs are outside this export policy and may still contain historical raw service output.

| Source        | Searchable diagnostic fields                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| Application   | Static startup, API failure, request failure, and redaction events; allowed HTTP method, route type, and status |
| MongoDB       | Bounded severity and numeric message ID                                                                         |
| Nginx gateway | Method, path-only URI, status, request/upstream timings, internal upstream address, response body bytes         |
| Alloy         | Bounded log level                                                                                               |

Unrecognized fields are omitted. Unknown raw output still produces a JSON redaction event rather than disappearing.

The gateway emits JSON access logs to stdout and warning/error logs to stderr. Its server-level access directive
overrides the image's inherited combined format, so each request produces one access entry. Access fields are `time`,
`method`, `uri`, `status`, `request_time`, `upstream_response_time`, `upstream_connect_time`, `upstream_header_time`,
`upstream_addr`, and `bytes_sent` (response body bytes). No request headers, cookies, Authorization, or query string are
included. Unknown methods become `UNKNOWN`. The URI is NGINX's normalized `$uri`; paths containing decoded query
delimiters, control characters, percent signs, quotes, unsupported characters, or more than 2,048 characters become
`/redacted`. Paths can contain application identifiers, so do not place credentials or session data in URL paths.

Alloy accepts only this exact bounded access schema. Legacy access entries, NGINX error output, and malformed or
augmented JSON become `gateway_output_redacted` events. Local stderr can contain request details generated by NGINX; the
fail-closed collector prevents these raw diagnostics from reaching Cloud. Upstream timings are strings because NGINX can
emit an empty string when no upstream was contacted, `-`, or multiple values separated by commas/colons during retries.
The upstream address can also be empty. Use numeric `request_time` for request duration queries; do not convert an
upstream timing list directly to a number.

Only bounded deployment and container context belongs in indexed labels. Release versions, request IDs, user IDs, URLs,
and payload fields must never become labels. Use JSON parsing at query time for allowed event fields.

## Verify in Grafana Explore

Open Grafana Explore in the target stack, select its Loki data source, and choose a time range containing representative
traffic. Synthetic Monitoring also uses `project="rusys"`, so select Docker containers explicitly when verifying this
pipeline.

```logql
{project="rusys", container=~"rusys-app-(blue|green)"}
```

```logql
{project="rusys", container="rusys-app-blue"} | json
```

```logql
{project="rusys", container="rusys-app-green"} | json
```

```logql
{project="rusys", container=~"rusys-(db|gateway|monitoring)"} | json
```

The actual Compose container name is `rusys-gateway`. Require a nonempty `uri` to select access records and exclude
redaction events or legacy history, then filter by status and request duration in seconds:

```logql
{project="rusys", container="rusys-gateway"} | json | uri != "" | __error__="" | status >= 400
```

```logql
{project="rusys", container="rusys-gateway"} | json | uri != "" | __error__="" | request_time >= 0.5
```

```logql
sum(count_over_time({project="rusys", container="rusys-gateway"} | json | uri != "" | __error__="" | status >= 100 [5m]))
```

```logql
quantile_over_time(0.95, {project="rusys", container="rusys-gateway"} | json | uri != "" | unwrap request_time | __error__="" [5m]) by (container)
```

Include a known 2xx response and a controlled failure when verifying status queries. Check that a request with dummy
query, Authorization, and Cookie values produces exactly one access entry and none of those values appear in its
exported JSON. Verify a numeric duration query against fresh traffic; a threshold of `0` also includes fast responses.
The p95 grouping removes parsed per-request fields, including timestamps, from result labels to bound the number of
query result series.

Check that both slots appear with their own container label and correct JSON slot/version fields. Confirm each exported
line parses as JSON and inspect its field names and allowed values. Avoid printing raw production logs to terminal
output while verifying privacy. Check that release versions and personal identifiers are absent from stream labels.
After recreating Alloy, confirm fresh entries still arrive; its persistent storage preserves Docker positions.

If entries are missing, inspect the loopback Alloy status UI through an SSH tunnel and check Docker discovery,
processing, and Loki write component health. A healthy container alone does not prove Cloud ingestion. Verify the
collector credentials and token scope without printing their values. Grafana queries use the data source's read access;
the collector token needs only write access.

## Configuration and acceptance

Validate gateway and collector configuration as part of the deployment pipeline. Confirm representative application and
access events arrive with the expected schema, bounded labels, and release/environment context. A configuration change
must preserve these contracts across supported deployment targets.

Regression tests for the supplied container integration:

```sh
pnpm exec vitest run scripts/nginx-logging.test.ts scripts/deploy.test.ts
RUN_DOCKER_TESTS=1 pnpm exec vitest run scripts/nginx-logging.test.ts
```

The opt-in tests use disposable containers and dummy sensitive values to verify gateway log formatting, single access
entries, sanitization, and collector filtering. Validate actual destination-side ingestion separately for every
environment.
